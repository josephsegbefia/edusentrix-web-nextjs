## 1. What changed

The code commit contains the full P1.3 storage-security working tree plus the two P1.3S corrections below.

### 1.1 Authorization ordering (student photo privacy)

**Problem.** In `authorizeStoredAssetRead` the special link token check (admission tracker token, document request token) ran before the student photo rule and did not look at the asset kind. The download gateway `GET /api/storage/assets/{id}?token=...` passes the query token straight into that check. A `student_avatar` with an `application` or `request` association could therefore be opened anonymously by anyone holding any matching token.

**Fix.** [`src/lib/storage/access-policy.ts`](../../src/lib/storage/access-policy.ts)

New read order:

1. Asset must be `ready`.
2. **Always-private kinds (`student_avatar`) are decided first** by `authorizeAlwaysPrivateRead`, and never reach the public, token, uploader, or association paths:
   - no actor or a public-token actor: denied
   - different school: denied
   - same-school school admin or platform operator (assisted access): allowed
   - otherwise `authorizeStudentAvatarRead`: Learn student's own photo, bursar, `students.view` delegate, homeroom or actively assigned teacher, guardian. Uploading a photo grants nothing.
3. Effectively public assets (teacher avatars, school branding): allowed.
4. Special link tokens only for `PUBLIC_TOKEN_READABLE_KINDS = {admission_document, parent_document}`. The kind must match the association type: an `application` token unlocks only `admission_document`, and a `request` token unlocks `admission_document` or `parent_document`.
5. Existing actor, school, admin, uploader, and association rules for every other kind.

The sync helper `canReadStoredAsset` follows the same order and also denies public-token actors. `canMutateStoredAsset` was already kind-gated and is unchanged.

Legitimate access preserved (all covered by tests): Web admin, assisted access, bursar, delegate, teacher, and guardian photo views; the Konect/Learn student's own photo through the signed URL route; admission and parent document token uploads and views; anonymous teacher avatars and school branding.

### 1.2 Migration dry run is strictly read-only

**Problem.** `scripts/storage/normalize-student-avatar-metadata.ts` imported the models at load time and connected through the shared `connectToDatabase`, which sets `autoIndex: NODE_ENV !== "production"`. Mongoose `autoCreate` is on by default. A dry run outside `NODE_ENV=production` therefore created collections and indexes. Reproduced on a disposable in-memory database: the old path created **2 collections and 15 indexes** on an empty database.

**Fix.** [`scripts/storage/normalize-student-avatar-metadata.ts`](../../scripts/storage/normalize-student-avatar-metadata.ts)

- `mongoose.set("autoIndex", false)` and `mongoose.set("autoCreate", false)` run before any model is compiled (the migration module is now a dynamic import). The script connects locally with `autoIndex: false, autoCreate: false` and never uses `connectToDatabase`. **No mode builds indexes or collections, and nothing depends on `NODE_ENV`.**
- In dry run, a driver-level write guard is installed before connecting. Every write method on the MongoDB driver `Collection` and `Db` (insert, update, replace, delete, bulkWrite, findOneAnd*, create/drop index, drop, rename, createCollection, dropDatabase), `aggregate` with `$out`/`$merge`, and write commands sent through `db.command` throw `Dry run attempted a write`. Reads are unaffected.
- Real writes need **all three**:
  1. `--apply` (with a new `--manifest <path>`) or `--rollback <manifest>`
  2. `CONFIRM_STUDENT_AVATAR_MIGRATION=yes`
  3. `--confirm-database <name>` equal to the database the script actually connected to (checked after connecting, before the manifest or any update is written)
- The script prints the host and database before doing anything.

### 2.2 Konect signed photo URL contract

`GET /api/storage/assets/{assetId}/url` ([route](../../src/app/api/storage/assets/[assetId]/url/route.ts)) is unchanged by P1.3S. It never forwards a `?token=` into the policy, so the token change cannot affect it. The existing contract tests pass:

- 401 with no session, with an invalid Bearer token, or with an expired Learn session, before any asset lookup.
- 403 for a suspended membership, a suspended school, cross-school access, or a member with no relationship to the student.
- 404 for a missing asset once signed in.
- 200 with exactly `{ "success": true, "data": { "url", "expiresAt", "expiresInSeconds" } }`, where `url` is a presigned R2 URL containing no `token=`.
- Headers `Cache-Control: private, no-store` and `Vary: Authorization, Cookie`.
- Learn Bearer session: own photo 200, another student's photo 403. Assisted access 200.
- Signed URL lifetime: `R2_SIGNED_URL_TTL_SECONDS`, default 120 seconds, allowed range 30 to 900.

Konect clients that already use this endpoint need no change.

### 3.5 Student avatar metadata migration (separate later step, not run here)

Access control does not depend on the migration: the kind rule already treats every `student_avatar` as private. The migration only normalizes metadata (marks photos `private` and links unambiguous legacy photos to their student). It also adds defense in depth (see 4.3). Run it only after the release is verified, as a separate approved operation:

```bash
# 1. Dry run (read-only, writes blocked). Review counts and ambiguous ids.
npx tsx scripts/storage/normalize-student-avatar-metadata.ts

# 2. Apply. Keep the manifest out of git and shared channels.
CONFIRM_STUDENT_AVATAR_MIGRATION=yes npx tsx scripts/storage/normalize-student-avatar-metadata.ts \
  --apply --manifest /secure/path/avatar-manifest-YYYYMMDD.json --confirm-database <production db name>

# 3. Rollback only if required (restores the previous visibility metadata and removes added links).
CONFIRM_STUDENT_AVATAR_MIGRATION=yes npx tsx scripts/storage/normalize-student-avatar-metadata.ts \
  --rollback /secure/path/avatar-manifest-YYYYMMDD.json --confirm-database <production db name>
```

Recommended: run the production dry run with a read-only MongoDB user. The code guard already blocks writes, and a read-only user adds a server-side guarantee.

## 4. Rollback and emergency mitigation

### 4.1 The key risk

The code currently on `master` (`688cf0ec` and every earlier commit) serves any asset whose stored `visibility` is `public` without authentication. Most existing student photos are stored as `public`. **Redeploying any image built from `688cf0ec` or earlier, including Coolify's "Rollback" to a previous deployment, makes student photos publicly downloadable again.** Treat a plain rollback as a security incident, not a neutral recovery.

### 4.2 Safe recovery order

1. **Roll forward (preferred).** Fix the problem on a branch from the new `master`, run `npm test` (at least the storage suites), merge, and let Coolify deploy.
2. **Targeted revert.** If one P1.3/P1.3S change misbehaves (for example an upload route), revert or patch only that file on top of `master`. Do not revert `f6faeaa0` as a whole, and do not revert `src/lib/storage/access-policy.ts` or `src/lib/storage/student-avatar-access.ts`.
3. **Coolify rollback only to a safe image.** Only roll back to a deployment whose commit contains `f6faeaa0` (check with `git merge-base --is-ancestor f6faeaa0 <deployed sha>`). Note in the Coolify deployment list which deployment is the first P1.3S one.
4. **If an old image is unavoidable** (the app is down and no safe image exists), apply one of the emergency mitigations below before or together with the rollback.

### 4.3 Emergency mitigations that keep student photos private

- **Apply the metadata migration (defense in depth).** After the migration, student photos are stored as `private`. The old code also refuses anonymous reads of private assets, so an old image would no longer expose them. On old code, teachers and parents would then lose photo access (only admins and the uploader can read), but nothing leaks. If rollback risk is a concern, running the migration soon after this release is verified is recommended. **Never run the migration rollback (manifest restore) while an old image is live**, because it puts `public` back.
- **Edge block.** If `tryedusentrix.app` is proxied by Cloudflare, add a temporary WAF rule that blocks `/api/storage/assets/*` requests without a session cookie (`__session`) and without an `Authorization` header. This also hides anonymous teacher avatars and school logos on public pages (cosmetic degradation, no data exposure). If the site is not proxied, an equivalent rule can go in the Coolify/Traefik proxy.
- **Keep R2 locked down.** Keep the R2 public dev URL disabled and do not attach a custom domain. Objects are then only reachable through app-issued presigned URLs, which expire after `R2_SIGNED_URL_TTL_SECONDS` (default 120 s). Any link leaked before a fix stops working within minutes.
- **Shorten link lifetime during an incident.** Setting `R2_SIGNED_URL_TTL_SECONDS=30` limits the reuse window of any issued link (requires a restart of the container).

## 5. Known residual items (not changed in this task)

- **Request token scope (non-photo documents).** A `request` token is matched against any document request in the asset's school, not the specific request the asset is associated with. Someone holding a valid request token could open another `request`-associated admission or parent document in the same school if they also had its 24-hex asset id. This cannot expose student photos after this fix. Recommended follow-up: bind request tokens to `association.id`.
- **Build-time database connection** during static generation (see section 2). This predates P1.3S.
- **Health check cold start** on `GET /api/healthz` (see 3.3). This predates P1.3S.
- **Mutation check not executed.** A temporary edit that would reintroduce the old token-first ordering, to watch the new tests fail, was blocked by the automated safety review and skipped. The regression tests target that exact path (a valid token on a `student_avatar` with an `application` or `request` association), and the pre-fix code shown in section 1.1 returns `allowed` there.
- **Baseline type and lint errors** listed in section 2 remain in unrelated modules.
