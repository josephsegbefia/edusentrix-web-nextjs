## 1. What changed

The code commit contains the full P1.3 storage-security working tree plus the two P1.3S corrections below.

### 1.1 Authorization ordering (student photo privacy)

**Problem.** In `authorizeStoredAssetRead` the special link token check (admission tracker token, document request token) ran before the student photo rule and did not look at the asset kind. The download gateway `GET /api/storage/assets/{id}?token=...` passes the query token straight into that check. A `student_avatar` with an `application` or `request` association could therefore be opened anonymously by anyone holding any matching token.

**Fix.** [`src/lib/storage/access-policy.ts`](../../src/lib/storage/access-policy.ts)

New read order:

1. Asset must be `ready`.
2. **Always-private kinds (`student_avatar`) are decided first** by `authorizeAlwaysPrivateRead`, and never reach the public, token, uploader, or association paths:
   - no actor or a public-token actor: denied
   - different school: denied
   - same-school school admin or platform operator (assisted access): allowed
   - otherwise `authorizeStudentAvatarRead`: Learn student's own photo, bursar, `students.view` delegate, homeroom or actively assigned teacher, guardian. Uploading a photo grants nothing.
3. Effectively public assets (teacher avatars, school branding): allowed.
4. Special link tokens only for `PUBLIC_TOKEN_READABLE_KINDS = {admission_document, parent_document}`. The kind must match the association type: an `application` token unlocks only `admission_document`, and a `request` token unlocks `admission_document` or `parent_document`. Section 1.3 narrows this further: each token now opens only its own request's or application's documents.
5. Existing actor, school, admin, uploader, and association rules for every other kind.

The sync helper `canReadStoredAsset` follows the same order and also denies public-token actors. `canMutateStoredAsset` was already kind-gated and is unchanged.

Legitimate access preserved (all covered by tests): Web admin, assisted access, bursar, delegate, teacher, and guardian photo views; the Konect/Learn student's own photo through the signed URL route; admission and parent document token uploads and views; anonymous teacher avatars and school branding.

### 1.2 Migration dry run is strictly read-only

**Problem.** `scripts/storage/normalize-student-avatar-metadata.ts` imported the models at load time and connected through the shared `connectToDatabase`, which sets `autoIndex: NODE_ENV !== "production"`. Mongoose `autoCreate` is on by default. A dry run outside `NODE_ENV=production` therefore created collections and indexes. Reproduced on a disposable in-memory database: the old path created **2 collections and 15 indexes** on an empty database.

**Fix.** [`scripts/storage/normalize-student-avatar-metadata.ts`](../../scripts/storage/normalize-student-avatar-metadata.ts)

- `mongoose.set("autoIndex", false)` and `mongoose.set("autoCreate", false)` run before any model is compiled (the migration module is now a dynamic import). The script connects locally with `autoIndex: false, autoCreate: false` and never uses `connectToDatabase`. **No mode builds indexes or collections, and nothing depends on `NODE_ENV`.**
- In dry run, a driver-level write guard is installed before connecting. Every write method on the MongoDB driver `Collection` and `Db` (insert, update, replace, delete, bulkWrite, findOneAnd*, create/drop index, drop, rename, createCollection, dropDatabase), `aggregate` with `$out`/`$merge`, and write commands sent through `db.command` throw `Dry run attempted a write`. Reads are unaffected.
- Real writes need **all three**:
  1. `--apply` (with a new `--manifest <path>`) or `--rollback <manifest>`
  2. `CONFIRM_STUDENT_AVATAR_MIGRATION=yes`
  3. `--confirm-database <name>` equal to the database the script actually connected to (checked after connecting, before the manifest or any update is written)
- The script prints the host and database before doing anything.

### 1.3 Document-token authorization closure

**How the tokens are bound.**

| Token | Stored at | Format | What it may open after this change |
| --- | --- | --- | --- |
| Admission tracker | `AdmissionApplication.tracker.token` | 32 hex | `admission_document` assets associated `{type: "application", id}` with that application's `_id` |
| Supplemental request | `AdmissionApplication.supplementalDocumentRequests[].token` (subdoc has `_id`) | 32 base64url | `admission_document` assets associated `{type: "request", id}` with that request's `_id` |
| Parent document request | `Student.parentDocumentRequests[].token` (subdoc has `_id`) | 32 base64url | `parent_document` assets associated `{type: "request", id}` with that request's `_id` (this is how the signed-in parent upload links its file) |

**Problem.** The tracker token was already bound to its application. Request tokens were not. A `request`-associated document was checked with `Student.findOne({schoolId, parentDocumentRequests: {$elemMatch: {token}}})` (and the same for supplemental requests), without the request id. **Any valid request token in a school opened every request-linked document in that school.** A `request` document was also checked against both stores, so parent and supplemental tokens were interchangeable. Reproduced on a disposable database: for a document belonging to another student's request, the old query matched and the new bound query did not.

Separately, `canMutateStoredAsset` let any public-token actor (including the anonymous public apply form, which resolves from `schoolId + cycleSlug`) complete or change **any** admission or parent document in the school. The download gateway also told anonymous callers apart: 404 for a missing id, 401 for an existing but forbidden one.

**Fix.**

- [`authorizeByPublicToken`](../../src/lib/storage/access-policy.ts) is now an explicit per-type matrix. Each kind and association pair is checked against exactly one token store, always with `schoolId: asset.schoolId` and the association id:
  - `application` + `admission_document` uses `AdmissionApplication {_id, schoolId, tracker.token}`
  - `request` + `admission_document` uses `AdmissionApplication {schoolId, supplementalDocumentRequests: {$elemMatch: {_id, token}}}`
  - `request` + `parent_document` uses `Student {schoolId, parentDocumentRequests: {$elemMatch: {_id, token}}}`
  - anything else: denied
  
  Tokens are trimmed and must be 16 to 128 characters. Invalid association ids are denied before any query.
- A token can no longer open a document from a different request, even in the same school, the same student, or the same application. Token types are strictly separated. Student photos and every other kind are still decided before this function and never reach it.
- **Missing, revoked, mismatched.** There is no expiry or revocation field in the current model. A token stops working when its request or application no longer exists (removed request, deleted application). A fulfilled request still opens its own document: this is the existing contract, kept on purpose so a parent can view what they uploaded.
- **Upload operations.** `StorageActor.publicTokenKind` is set by [`resolvePublicUploadActor`](../../src/lib/storage/public-token.ts). [`canMutateStoredAsset`](../../src/lib/storage/access-policy.ts) lets a public-token actor act only on an asset of exactly its token kind that has no uploader (`uploadedByUserId` null) and no association. It can no longer finalize a signed-in parent's upload, a document already linked to a record, or the other token type's files. Public rollback already had this scope.
- **No existence leaks.** [`grantAssetDownload`](../../src/lib/storage/service.ts) gives anonymous callers (with or without `?token=`) one identical response for a malformed id, a missing asset, an unfinished or deleted asset, and a forbidden asset: **401 `{ "success": false, "error": "Not allowed to download this file" }`**, with no `Location` header and no file name, kind, or school. Signed-in callers keep 404 (missing) and 403 (forbidden), so the Konect `/url` contract is unchanged.

No code in this repository calls the gateway with `?token=`, and Konect uses the Bearer `/url` route, which never takes a token. These changes therefore do not alter any current Web or Konect screen. They only close the direct-link path.

## 4. Rollback and emergency mitigation

### 4.1 The key risk

The code currently on `master` (`688cf0ec` and every earlier commit) serves any asset whose stored `visibility` is `public` without authentication. Most existing student photos are stored as `public`. **Redeploying any image built from `688cf0ec` or earlier, including Coolify's "Rollback" to a previous deployment, makes student photos publicly downloadable again.** Treat a plain rollback as a security incident, not a neutral recovery.

### 4.2 Safe recovery order

1. **Roll forward (preferred).** Fix the problem on a branch from the new `master`, run `npm test` (at least the storage suites), merge, and let Coolify deploy.
2. **Targeted revert.** If one P1.3/P1.3S change misbehaves (for example an upload route), revert or patch only that file on top of `master`. Do not revert `f6faeaa0` or the document-token closure commit as a whole. Do not revert `src/lib/storage/access-policy.ts`, `src/lib/storage/student-avatar-access.ts`, or the `grantAssetDownload` and `canMutateStoredAsset` changes.
3. **Coolify rollback only to a safe image.** Only roll back to a deployment whose commit contains `f6faeaa0` (check with `git merge-base --is-ancestor f6faeaa0 <deployed sha>`). Note in the Coolify deployment list which deployment is the first P1.3S one.
4. **If an old image is unavoidable** (the app is down and no safe image exists), apply one of the emergency mitigations below before or together with the rollback.

### 4.3 Emergency mitigations that keep student photos private

- **Apply the metadata migration (defense in depth).** After the migration, student photos are stored as `private`. The old code also refuses anonymous reads of private assets, so an old image would no longer expose them. On old code, teachers and parents would then lose photo access (only admins and the uploader can read), but nothing leaks. If rollback risk is a concern, running the migration soon after this release is verified is recommended. **Never run the migration rollback (manifest restore) while an old image is live**, because it puts `public` back.
- **Edge block.** If `tryedusentrix.app` is proxied by Cloudflare, add a temporary WAF rule that blocks `/api/storage/assets/*` requests without a session cookie (`__session`) and without an `Authorization` header. This also hides anonymous teacher avatars and school logos on public pages (cosmetic degradation, no data exposure). If the site is not proxied, an equivalent rule can go in the Coolify/Traefik proxy.
- **Keep R2 locked down.** Keep the R2 public dev URL disabled and do not attach a custom domain. Objects are then only reachable through app-issued presigned URLs, which expire after `R2_SIGNED_URL_TTL_SECONDS` (default 120 s). Any link leaked before a fix stops working within minutes.
- **Shorten link lifetime during an incident.** Setting `R2_SIGNED_URL_TTL_SECONDS=30` limits the reuse window of any issued link (requires a restart of the container).

## 5. Known residual items (not changed in this task)

- **Request token scope:** closed in commit 3 (section 1.3). Tokens are now bound to their own request or application.
- **Signed-in existence signal.** Signed-in callers still get 404 for a missing asset and 403 for a forbidden one, to keep the Konect `/url` contract. A signed-in member of any school can therefore tell whether an asset id exists, but never read it. Asset ids are MongoDB ObjectIds, which are partly sequential, so ids are guessable near a known one. Content and metadata stay protected. Making signed-in denials 404 would need a coordinated Konect change.
- **Public apply form uploads.** The public application form resolves a public-token actor from `schoolId + cycleSlug`, which anyone can obtain for a published cycle. That actor may finalize a *pending, anonymous, unlinked* `admission_document` upload in that school if it knows the asset id. This grants no read access, and signed-in or linked documents are now excluded. Closing it fully needs a per-upload binding (for example a hashed upload grant stored on the asset).
- **Token lifecycle.** Tokens are stored in plain text and have no expiry or revocation fields. A token works until its request or application is removed, and a fulfilled request still opens its own document (existing contract). Recommended follow-up: hash stored tokens, add `expiresAt` and `revokedAt`, and decide whether fulfilled requests should keep read access.
- **Build-time database connection** during static generation (see section 2). This predates P1.3S.
- **Health check cold start** on `GET /api/healthz` (see 3.3). This predates P1.3S.
- **Mutation check not executed for the photo ordering fix.** A temporary edit that would reintroduce the old token-first ordering, to watch the new tests fail, was blocked by the automated safety review and skipped. The regression tests target that exact path (a valid token on a `student_avatar` with an `application` or `request` association), and the pre-fix code shown in section 1.1 returns `allowed` there. For the document-token gap, the old and new query shapes were compared directly on a disposable database without touching product code (old: granted, new: denied).
- **Baseline type and lint errors** listed in section 2 remain in unrelated modules.
